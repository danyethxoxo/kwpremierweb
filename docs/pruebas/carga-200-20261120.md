# Prueba real de 200 busquedas simultaneas

Fecha: 20 de noviembre de 2026. Proyecto: KWEB, Supabase Free, sin cambios de plan ni compute.

## Resultado observado

| Escenario | Peticiones simultaneas | Respuestas correctas | Tiempo p95 | Tiempo maximo observado |
| --- | ---: | ---: | ---: | ---: |
| Misma busqueda repetida | 200 | 200 | 3,170 ms | 3,286 ms |
| Mezcla de ocho filtros | 200 | 195 | 11,645 ms | 12,014 ms |

En el segundo escenario, cinco peticiones agotaron el limite del cliente de 12 segundos. El resultado no demuestra cinco errores del servidor: algunas consultas pueden terminar despues de que el cliente deje de esperar. El objetivo de 200 consultas variadas sin fallos no se cumplio.

Datos: [repetida](carga-200-repetida-20261120.json) y [variada](carga-200-variada-20261120.json).

## Metodo y alcance

- Peticiones HTTP POST reales al RPC propiedades_inventario_pagina a traves de data-gateway, con JWT valido y consultas a la base de datos de produccion. No se simularon los servicios.
- Generador Node externo a Supabase. Escalones de 5, 25, 50 y 200 peticiones, una ronda por escalon y 1.5 segundos entre escalones: 280 peticiones por escenario, 560 entre ambos.
- Una cuenta temporal por escenario. Se midieron 200 consultas en vuelo, no 200 personas distintas ni 200 inicios de sesion.
- La cache del sistema permanecio activa. La mezcla incluyo inventario reciente, CDMX, venta, renta, casas, departamentos y filtros de precio. Son ocho combinaciones repetidas, no 200 busquedas distintas con cache fria.
- El generador consumio y valido la estructura JSON de las respuestas. La prueba no revisa manualmente cada ficha ni la congruencia de sus datos.
- Se corto la carga al detectar errores o un p95 superior a 10 segundos. Ese corte es una medida de proteccion, no una promesa de latencia aceptable.

Un primer intento dentro de una Edge Function completo los escalones de 5 y 25, pero el generador produjo fallos sin respuesta HTTP al subir a 50. Se descarto como medicion de capacidad del sitio y se repitio desde Node externo. No se atribuyen esos fallos a la base de datos sin evidencia.

## Datos y limpieza

Las cuentas sinteticas no generaron perfiles de asociados ni invocaron el envio de codigos. Se utilizaron solo lecturas de inventario y escrituras tecnicas normales de controles/cache. No se modificaron propiedades.

Las credenciales fueron generadas en el servidor. La sesion se transfirio cifrada con RSA-OAEP y AES-GCM al generador; las llaves privadas y tokens permanecieron en memoria y no se incluyeron en informes ni archivos. Cada sesion se revoco al terminar, las cuentas se eliminaron y se verifico que no quedaran cuentas marcadas como prueba.

El servicio temporal kweb-carga-20261120 quedo retirado: version 3, JWT obligatorio y respuesta 410, sin codigo para crear cuentas o ejecutar pruebas. El chequeo de acceso real del portal y Auth paso despues de la prueba.

## Conclusion limitada

La configuracion actual resolvio el pico de 200 consultas repetidas en esta ejecucion. No sostuvo la mezcla medida dentro del tiempo de espera del cliente. No esta certificado el objetivo completo de 200 consultas variadas ni accesos nuevos concurrentes. El siguiente ensayo debe medir el cuello de botella y repetirse con la capacidad de infraestructura elegida, sin ocultar el problema ampliando simplemente los tiempos de espera.
